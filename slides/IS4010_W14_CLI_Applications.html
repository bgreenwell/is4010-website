Session 1: from raw arguments to clap

A CLI is a function

  arguments                       output
  Homer --times 2  ──→  program  ──→  text on stdout
                                      errors on stderr
                                      exit code (0 = success)
  • In: a list of strings typed after the program name.
  • Out: printed text, plus a number that tells scripts whether it worked.

Everything this week is about turning that list of strings into typed values, safely.

Students used CLIs all semester: git, uv, cargo, pytest. In Week 08 they built a Python CLI with argparse; today is the Rust equivalent. The exit code is invisible in normal use but matters to scripts and CI: GitHub Actions marks a step red when a command exits nonzero, which is exactly how the lab badges work.

Anatomy of a command

cargo run -- random --length 16 --symbols
Piece Name Meaning
cargo run Runner Build the project, then start it
-- Separator Everything after this goes to our program, not to Cargo
random Subcommand Which action to take
--length 16 Option A named value
--symbols Flag On if present, off if absent

The – trips students up. Without it, Cargo would try to interpret –length itself and fail. After building, the same command runs directly as target/debug/week14 random –length 16 –symbols, with no cargo and no –.

Reading arguments by hand

use std::env;

fn main() {
    let args: Vec<String> = env::args().collect();
    println!("{:?}", args);
}
$ cargo run -q -- needle haystack
["target/debug/args", "needle", "haystack"]
  • env::args() returns an iterator over the arguments; collect gathers them (Week 13).
  • args[0] is the program’s own path. Your values start at args[1].

Rust Book listing 12-1, using println! with {:?} in place of dbg!. Students often expect args[0] to be the first value they typed; it is the program. Everything arrives as a String, even numbers: turning “2” into a u32 is our job.

Turning strings into typed values

use std::env;
use std::process;

struct Config {
    name: String,
    times: u32,
}

impl Config {
    fn build(args: &[String]) -> Result<Config, String> {
        if args.len() < 3 {
            return Err(String::from("usage: greet NAME TIMES"));
        }
        let name = args[1].clone();
        let times = args[2]
            .parse()
            .map_err(|_| format!("TIMES must be a number, got {:?}", args[2]))?;
        Ok(Config { name, times })
    }
}
  • A Config struct holds the typed values the program needs.
  • Config::build returns a Result (Week 13): check the count, parse the number, report problems.

This follows Rust Book 12.3: a Config struct and a build function that returns Result instead of panicking. map_err and ? are the Week 13 error patterns. Clone copies the name out of the argument list so Config owns its own String (Week 10).

main decides how to report errors

fn main() {
    let args: Vec<String> = env::args().collect();

    let config = Config::build(&args).unwrap_or_else(|err| {
        eprintln!("Error: {}", err);
        process::exit(1);
    });

    for _ in 0..config.times {
        println!("Hello, {}!", config.name);
    }
}
$ cargo run -q -- Homer 2
Hello, Homer!
Hello, Homer!
$ cargo run -q -- Homer
Error: usage: greet NAME TIMES
$ cargo run -q -- Homer two
Error: TIMES must be a number, got "two"
  • unwrap_or_else prints the error to stderr with eprintln! and exits with code 1.
  • Still missing: --help, named options like --times, flags, and defaults. Each one is more code to write by hand.

Rust Book 12.3 and 12.6: main decides how to report errors, and eprintln! writes to stderr so error messages do not mix with real output when the output is redirected to a file. process::exit(1) stops the program with a failure code. This is the point to introduce clap: describe the arguments as data, and let a library write the parser.

The same tool with clap

use clap::Parser;

/// Greet someone, one or more times
#[derive(Parser)]
#[command(name = "greet", version)]
struct Cli {
    /// Who to greet
    name: String,

    /// How many times to greet them
    #[arg(short, long, default_value_t = 1)]
    times: u32,

    /// Shout the greeting
    #[arg(short, long)]
    loud: bool,
}

fn main() {
    let cli = Cli::parse();

    for _ in 0..cli.times {
        let greeting = format!("Hello, {}!", cli.name);
        if cli.loud {
            println!("{}", greeting.to_uppercase());
        } else {
            println!("{}", greeting);
        }
    }
}

Why: The struct is the interface. Each field becomes an argument; clap writes the parsing code.

Compare with the hand-written version: no args vector, no index checks, no parse call, no usage string. #[derive(Parser)] generates the parser from the struct, the same way #[derive(Debug)] generated formatting in Week 12. Cli::parse() reads the real arguments and either returns a filled-in Cli or prints an error and exits.

clap writes the help screen

$ cargo run -q -- --help
Greet someone, one or more times

Usage: greet [OPTIONS] <NAME>

Arguments:
  <NAME>  Who to greet

Options:
  -t, --times <TIMES>  How many times to greet them [default: 1]
  -l, --loud           Shout the greeting
  -h, --help           Print help
  -V, --version        Print version
  • Every line comes from the struct: field names, /// doc comments, and the default.
  • -h, --help, -V, and --version are added automatically.

Real output. Ask students to find each struct field in the help text. The [OPTIONS] and in the usage line come from the field kinds: named options versus the required positional name.

clap parses and checks the input

$ cargo run -q -- Homer --times 2
Hello, Homer!
Hello, Homer!
$ cargo run -q -- Homer -t 2 --loud
HELLO, HOMER!
HELLO, HOMER!
$ cargo run -q -- Homer --times two
error: invalid value 'two' for '--times <TIMES>': invalid digit found in string

For more information, try '--help'.
  • Short and long options, a default for --times, and a flag for --loud.
  • Bad input gets a clear error and exit code 2 before your code runs.

Real output. Compare with the hand-written error messages two slides back: clap’s version names the option, the bad value, and the reason, and points to –help.

Read the attributes aloud

Code Read it as Command line
#[derive(Parser)] Build a parser from this struct
/// Who to greet Help text for the next field Shown by --help
name: String A required positional argument Homer
#[arg(short, long)] Accept -t and --times --times 2
default_value_t = 1 Use 1 if the option is missing
loud: bool with #[arg(short, long)] A flag --loud

The field’s type does the validation: times: u32 rejects two and -1 automatically.

A field without #[arg] is positional; with #[arg(short, long)] it becomes a named option; a bool option becomes a flag. An Option field would make an option optional without a default. Point students to the clap derive tutorial in the resources for more.

Subcommands are an enum

use clap::{Parser, Subcommand};

/// A tiny calculator
#[derive(Parser)]
#[command(name = "calc", version)]
struct Cli {
    #[command(subcommand)]
    command: Commands,
}

#[derive(Subcommand)]
enum Commands {
    /// Add two numbers
    Add { a: i32, b: i32 },

    /// Square a number
    Square {
        n: i32,

        /// Show the work
        #[arg(short, long)]
        verbose: bool,
    },
}
fn main() {
    let cli = Cli::parse();

    match cli.command {
        Commands::Add { a, b } => println!("{}", a + b),
        Commands::Square { n, verbose } => {
            if verbose {
                println!("{} * {} = {}", n, n, n * n);
            } else {
                println!("{}", n * n);
            }
        }
    }
}
  • Each enum variant is a subcommand; its fields are that subcommand’s arguments.
  • match routes each subcommand to its code (Week 11).

This is the same shape as git commit / git push or cargo build / cargo test. #[command(subcommand)] tells clap the command field holds the enum. Because match must handle every variant, adding a subcommand without handling it is a compile error, not a forgotten branch.

Session 2: building the capstone

From parser to program

src/
├── main.rs       # Parse, route, print
├── generator.rs  # Passwords, passphrases, PINs
└── validator.rs  # Strength, patterns, entropy
tests/
└── cli.rs        # Run the program, check output
mod generator; // Loads src/generator.rs (Week 11)
mod validator;

use generator::{generate_passphrase, generate_pin, generate_random};

main.rs stays thin. The logic lives in modules that can be tested without the command line.

This is the book’s chapter 12 advice (“separation of concerns for binary projects”) applied to the lab. generator.rs and validator.rs each have their own unit tests; tests/cli.rs runs the compiled program. The mod and use lines are already in the lab’s main.rs.

Randomness comes from a crate

use rand::seq::SliceRandom;
use rand::Rng;

fn main() {
    let mut rng = rand::thread_rng();

    let roll = rng.gen_range(1..=6); // 1 through 6, inclusive
    let heads = rng.gen_bool(0.5); // true half the time
    let names = ["Homer", "Marge", "Bart", "Lisa", "Maggie"];
    let pick = names.choose(&mut rng); // Option<&&str>

    println!("Roll: {}", roll);
    println!("Heads? {}", heads);
    println!("Pick: {:?}", pick);

    let rolls: Vec<String> = (0..5).map(|_| rng.gen_range(1..=6).to_string()).collect();
    println!("Five rolls: {}", rolls.join(" "));
}
$ cargo run -q
Roll: 2
Heads? true
Pick: Some("Marge")
Five rolls: 6 3 5 4 2

Your output will differ: it is random.

Python ships random in the standard library; Rust keeps randomness in the rand crate. thread_rng gives a generator; gen_range picks from a range (1..=6 includes 6, 1..6 would not); choose picks from a slice and returns an Option because the slice might be empty. The last example builds a String with an iterator, the Week 13 pattern. These are general tools, not the lab’s functions.

Check your crate version

Lab 14 pins rand = "0.8". Newer rand releases renamed these functions:

rand 0.8 (Lab 14) rand 0.9 and later
rand::thread_rng() rand::rng()
rng.gen_range(1..=6) rng.random_range(1..=6)
rng.gen_bool(0.5) rng.random_bool(0.5)
  • The new names do not exist in 0.8: rand::rng() fails with E0423 in Lab 14.
  • The old names still work in 0.9 but are deprecated, and cargo clippy -- -D warnings turns that warning into a failure.
  • Search answers and AI assistants often show the newer API. Tell them your version, or check Cargo.toml first.
  • Read the docs for your version: docs.rs/rand/0.8.

Both directions were checked against real builds. This is a real trap: the default docs.rs page shows the latest rand, and many recent examples use rand::rng(). Lab 14’s Cargo.lock pins rand 0.8.5 and clap 4.5.60; students should not upgrade them. Good habit for any project: when an example does not compile, compare its crate version with yours.

Output is part of the contract

Lab 14’s integration tests run the finished program and check what it prints:

fn run(args: &[&str]) -> Output {
    Command::new(env!("CARGO_BIN_EXE_week14"))
        .args(args)
        .output()
        .expect("the Week 14 binary should run")
}

#[test]
fn pin_command_prints_requested_digits() {
    let text = stdout(&run(&["pin", "--length", "8"]));
    let pin = text
        .trim()
        .strip_prefix("Generated PIN: ")
        .expect("pin command should print a PIN");
    assert_eq!(pin.len(), 8);
    assert!(pin.chars().all(|character| character.is_ascii_digit()));
}
Subcommand Required output
random Generated password: ... then Entropy: ... bits
passphrase Generated passphrase: ...
pin Generated PIN: ...
validate Password strength: ..., Entropy: ... bits, and Warning: ... for weak patterns

Integration tests live in tests/ and treat the program as a black box: std::process::Command runs the compiled binary with arguments, exactly as a user or a script would. env!(“CARGO_BIN_EXE_week14”) is the path Cargo gives the test. The same prefixes are listed in lab14.md and in the TODO comments in main.rs. Other programs and scripts depend on output formats in the same way, which is why changing them is a breaking change.

Exit codes tell scripts what happened

$ cargo run -q -- Homer --times two
error: invalid value ...
$ echo $?
2
$ cargo run -q -- Homer --times 2 > /dev/null
$ echo $?
0
Code Meaning Who sets it
0 Success Returning normally from main
1 Your program reported an error process::exit(1)
2 Bad command-line usage clap, automatically
  • Errors go to stderr (eprintln!), so > file captures only the real output.

echo $? prints the previous command’s exit code in bash and zsh (PowerShell uses $LASTEXITCODE). The first run is the greet program with a bad –times value; its error line is shortened here. CI systems and the lab badges rely on exactly this: a failing test makes cargo test exit nonzero, and the workflow turns red.
