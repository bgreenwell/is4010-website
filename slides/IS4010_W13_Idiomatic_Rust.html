One idea runs through this week

Session 1: closures and iterators

Functions you can write inline

fn add_one_v1(x: u32) -> u32 {
    x + 1
}

fn main() {
    let add_one_v2 = |x: u32| -> u32 { x + 1 };
    let add_one_v3 = |x: u32| x + 1;
    let add_one_v4 = |x| x + 1;

    println!("{}", add_one_v1(5)); // 6
    println!("{}", add_one_v2(5)); // 6
    println!("{}", add_one_v3(5)); // 6
    println!("{}", add_one_v4(5)); // 6
}
  • A closure is a function without a name: |x| x + 1.
  • Read |x| as “given x.” The body follows.
  • Types are optional when Rust can infer them.

Try this example in Rust Playground

Output: 6 four times. This is the Rust Book’s add_one_v1 through add_one_v4 comparison from 13.1. Each version drops something optional: the return type, the braces, then the parameter type. Python parallel: lambda x: x + 1. Rust closures can have multi-line bodies in braces, which Python lambdas cannot.

Closures can capture values

fn main() {
    let threshold = 10;

    // The closure uses threshold from main
    let is_large = |x: i32| x > threshold;

    println!("{}", is_large(5)); // false
    println!("{}", is_large(15)); // true
}

Predict: Could a regular fn is_large inside main use threshold?

No: E0434: can't capture dynamic environment in a fn item. Only closures can see variables around them.

Try this example in Rust Playground

Output: false, then true. The ability to capture is what makes closures useful as arguments to filter and map later: the closure brings its own data, such as a threshold, along with it. Demonstrate the fn version from the fragment if time allows.

Capturing to read or to change

fn main() {
    let mut list = vec![1, 2, 3];

    // Borrows list for reading, like &list
    let print_list = || println!("Closure sees: {:?}", list);
    print_list(); // Closure sees: [1, 2, 3]
    println!("Main still sees: {:?}", list); // Main still sees: [1, 2, 3]

    // Borrows list for changing, like &mut list
    let mut add_seven = || list.push(7);
    add_seven();
    println!("After push: {:?}", list); // After push: [1, 2, 3, 7]
}
  • print_list only reads list, so it borrows like &list. Main can still read it too.
  • add_seven changes list, so it borrows like &mut list, and must be declared let mut.

Try this example in Rust Playground

Book listings 13-4 and 13-5. Output: Closure sees: [1, 2, 3], Main still sees: [1, 2, 3], After push: [1, 2, 3, 7]. Rust picks the least access the body needs. Ask: what happens if you try to print list between creating add_seven and calling it? E0502, the reader/editor conflict from Week 10, because the closure holds a mutable borrow until its last use.

Capturing to own: move and FnOnce

fn main() {
    let name = String::from("Homer");

    // Moves name into the closure, then gives it away when called
    let take_name = move || name;

    let owner = take_name();
    println!("{}", owner); // Homer
}
  • move makes the closure take ownership of name.
  • Calling it gives name away, so it can be called only once: an FnOnce closure.

Predict: What happens if we call take_name() a second time?

E0382: use of moved value: take_name. The value was already given away on the first call.

Try this example in Rust Playground

Output: Homer. The body returns the captured String, which moves it out of the closure. This is the “own” row of the table. Most closures are Fn or FnMut; FnOnce matters when a closure hands away something it owns.

The three closure traits

Trait The closure… Week 10 equivalent Can call
Fn Only reads what it captured & Many times
FnMut Changes what it captured &mut Many times, needs let mut
FnOnce Gives away what it captured Ownership moves Once

Rust picks the trait from what the body does. You only write the trait names when a function accepts or returns a closure.

Fn closures also count as FnMut and FnOnce, and FnMut closures also count as FnOnce: a closure that only reads can certainly be called once. Students need that only when reading signatures such as sort_by_key, which takes FnMut. The next slide shows a function returning a closure.

Returning a closure

fn make_adder(n: i32) -> impl Fn(i32) -> i32 {
    move |x| x + n
}

fn main() {
    let add_five = make_adder(5);
    let add_ten = make_adder(10);

    println!("{}", add_five(1)); // 6
    println!("{}", add_ten(1)); // 11
}
  • impl Fn(i32) -> i32: “some closure that takes an i32 and returns an i32” (Week 12’s impl Trait).
  • move copies n into the closure, so it still exists after make_adder returns.

Predict: What happens without move?

E0373: closure may outlive the current function, but it borrows n. Without move, the closure would hold a reference to a local variable that is about to disappear (Week 10’s dangling reference).

Try this example in Rust Playground

Output: 6, then 11. Each call to make_adder builds a separate closure with its own n. Lab 13’s make_counter uses the same shape, a returned closure with move, combined with the state-changing idea on the next slide; do not show the lab solution itself.

A closure that remembers

fn main() {
    let mut total = 0;

    let mut add_to_total = |amount| {
        total += amount;
        total
    };

    println!("{}", add_to_total(4)); // 4
    println!("{}", add_to_total(7)); // 11
}
  • The closure changes total each time it runs, so it is FnMut.
  • total keeps its value between calls: the closure has state.

Try this example in Rust Playground

Output: 4, then 11. Ask students which row of the access table this is (change, &mut) and why the closure binding needs let mut. While add_to_total may still be called, main cannot use total directly; the mutable borrow is active.

The problem: a loop with bookkeeping

fn main() {
    let numbers = [1, 2, 3, 4, 5, 6];
    let mut result = Vec::new();

    for n in numbers {
        if n % 2 == 0 {
            result.push(n * n);
        }
    }

    println!("{:?}", result); // [4, 16, 36]
}
  • The goal: squares of the even numbers.
  • The bookkeeping: an empty vector, if, push, mut.

Can we write just the goal?

Try this example in Rust Playground

Output: [4, 16, 36]. Nothing is wrong with this loop; it is clear and fast. The point is that most of the lines manage the result rather than describe it. Iterators let us write the three steps (keep evens, square, collect) directly.

An iterator is a bookmark

fn main() {
    let v = [1, 2, 3];
    let mut iter = v.iter();

    println!("{:?}", iter.next()); // Some(1)
    println!("{:?}", iter.next()); // Some(2)
    println!("{:?}", iter.next()); // Some(3)
    println!("{:?}", iter.next()); // None
}
Method Items Access
.iter() &T Read
.iter_mut() &mut T Change
.into_iter() T Own
  • Each call to next() returns the next item, then None at the end.
  • for loops call next() for you.

Try this example in Rust Playground

Book listing 13-12, written as a program instead of a test. Output: Some(1), Some(2), Some(3), None. The iterator remembers its position, which is why it must be mut: next changes the bookmark. The method table is the “iterators” column of the access map from the start of the session.

Python parallel: iter() and next(), with None in place of StopIteration.

Adaptors are lazy

This example compiles with a warning, and the map never runs.

fn main() {
    let v = [1, 2, 3];

    v.iter().map(|x| x + 1);

    println!("{:?}", v);
}
warning: unused `Map` that must be used
  = note: iterators are lazy and do nothing unless consumed

Fix: consume the iterator. collect() runs the chain and gathers the results.

fn main() {
    let v = [1, 2, 3];

    let plus_one: Vec<i32> = v.iter().map(|x| x + 1).collect();

    println!("{:?}", plus_one); // [2, 3, 4]
}

Try the fixed version in Rust Playground

Book listings 13-14 and 13-15. Adaptors such as map and filter describe work; consumers such as collect, sum, and count do it. This laziness is why long chains do not build a temporary vector at every step. Fixed output: [2, 3, 4]. The type annotation Vec tells collect what to build.

Chain adaptors: write just the goal

fn main() {
    let numbers = [1, 2, 3, 4, 5, 6];

    let result: Vec<i32> = numbers
        .into_iter()
        .filter(|n| n % 2 == 0) // Keep evens
        .map(|n| n * n) // Square them
        .collect();

    println!("{:?}", result); // [4, 16, 36]
}

Read it aloud: take the numbers, keep the evens, square them, collect into a vector.

Try this example in Rust Playground

Output: [4, 16, 36], matching the loop. into_iter on an array gives owned i32 values, so the closures receive plain numbers; with .iter() they would receive references and the patterns get noisier (|&&n| in older code). Ask students to compare the two versions line by line: same behavior, but the steps now read in order. Neither is always better; choose the one the team can read and test.

Common adaptors and consumers

fn main() {
    let numbers = [1, 2, 3, 4];
    let words = ["1", "two", "3"];

    let doubled: Vec<i32> = numbers.iter().map(|x| x * 2).collect();
    let parsed: Vec<i32> = words.iter().filter_map(|s| s.parse().ok()).collect();
    let total: i32 = numbers.iter().sum();
    let digits = numbers.iter().fold(0, |acc, x| acc * 10 + x);
    let evens = numbers.iter().filter(|x| *x % 2 == 0).count();
    let biggest = numbers.iter().max();

    println!("map:        {:?}", doubled); // [2, 4, 6, 8]
    println!("filter_map: {:?}", parsed); // [1, 3]
    println!("sum:        {}", total); // 10
    println!("fold:       {}", digits); // 1234
    println!("count:      {}", evens); // 2
    println!("max:        {:?}", biggest); // Some(4)
}
  • Adaptors return another iterator: map, filter, filter_map.
  • Consumers produce a result: collect, sum, fold, count, max.

Try this example in Rust Playground

filter_map keeps the Some values and drops the None values, here turning text into numbers and skipping “two”. fold carries an accumulator through the items; here it builds 1234 from the digits. max returns an Option because an empty list has no maximum. Note for Lab 13: max_by_key returns the last of several equal maxima, which matters when two words tie for longest.

Closures inside iterator chains

struct Student {
    name: String,
    grade: f64,
}

impl Student {
    fn new(name: &str, grade: f64) -> Student {
        Student {
            name: name.to_string(),
            grade,
        }
    }
}

fn honor_roll(students: &[Student], cutoff: f64) -> Vec<&str> {
    students
        .iter()
        .filter(|s| s.grade >= cutoff)
        .map(|s| s.name.as_str())
        .collect()
}
fn main() {
    let students = [
        Student::new("Lisa", 98.0),
        Student::new("Bart", 61.0),
        Student::new("Milhouse", 85.0),
    ];

    let honors = honor_roll(&students, 80.0);
    println!("{:?}", honors); // ["Lisa", "Milhouse"]
}

Why: The filter closure captures cutoff from the function, just like threshold earlier.

Try this example in Rust Playground

Output: [“Lisa”, “Milhouse”]. This mirrors the book’s shoes_in_size example in 13.2. Trace the item type after each step: iter gives &Student, filter keeps &Student, map turns each into &str, collect builds Vec<&str>. The result borrows names from students, so students must outlive it (Week 10).

Session 2: smart pointers and errors

References are pointers too

A pointer is a value that holds the location of another value. You have used one kind since Week 10.

Reference: &T, &mut T Smart pointer: Box, Rc, RefCell
Points to a value stored elsewhere Yes Yes
Owns that value No, it borrows Yes
When it goes away Nothing is freed It cleans up the value
Rules checked When compiling When compiling (RefCell: while running)
You have already used &str, &[i32] String, Vec<T>

A reference borrows a value. A smart pointer owns it and adds one ability a plain owner lacks.

  • Box<T>: keep the value on the heap
  • Rc<T>: let several owners share it
  • RefCell<T>: change it through a shared handle

Rust Book 15 intro. The first two rows are the whole idea: both kinds point, only smart pointers own. String and Vec already count, since each owns a heap buffer and frees it when dropped. Every example this session uses one tiny Song struct from a music app, so the only new thing on each slide is the pointer. Stress the order of preference: plain ownership and references first, smart pointers only when the design needs them.

Box<T>: one owner, data on the heap

Normally a value sits on the stack, and Rust must know its exact size when compiling (Week 10). Box::new(value) moves the value to the heap and keeps only a small pointer on the stack.

stack: song ──→ heap: Song { title: "Midnight Drive", ... }
  • A Box has one owner, like any value. When the owner goes out of scope, the heap value is freed.
  • A Box always has the same size, whatever it points to.

When to use it:

  • A type that contains itself, so Rust cannot work out its size
  • A large value you want to hand off without copying all its bytes

Rust Book 15.1. Connect to Week 10’s stack and heap slide. The second use is less common in student code; the first is the one the next two slides show. The book makes the same point with a cons list; a song that knows the next song is the same shape.

A song that contains the next song

A music app wants each song to know which song plays next.

This example intentionally fails to compile.

struct Song {
    title: String,
    next: Option<Song>,
}

fn main() {
    let last = Song {
        title: String::from("Sunrise"),
        next: None,
    };
    let first = Song {
        title: String::from("Midnight Drive"),
        next: Some(last),
    };
    println!("{}", first.title);
}
error[E0072]: recursive type `Song` has infinite size
help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle

Why: A Song holds a whole Song, which holds a whole Song, with no end. Option does not help: Some(song) still stores the entire song inside.

Try this example in Rust Playground

Ask how big a Song is: a title plus a whole Song, which is a title plus a whole Song, and so on. Draw nested boxes on the board. The help line names the fix.

Box fixes it: point to the next song

struct Song {
    title: String,
    next: Option<Box<Song>>,
}

fn play(song: &Song) {
    println!("Now playing: {}", song.title);
    if let Some(next) = &song.next {
        play(next);
    }
}

fn main() {
    let last = Song {
        title: String::from("Sunrise"),
        next: None,
    };
    let first = Song {
        title: String::from("Midnight Drive"),
        next: Some(Box::new(last)),
    };
    play(&first);
}
Now playing: Midnight Drive
Now playing: Sunrise

Why it works: “contains a song” became “points to a song.” The pointer is a fixed size, so Song is too.

Try this example in Rust Playground

The only change from the last slide is Box and Box::new. play calls itself until a song has no next song. Passing next (a &Box) where play expects &Song works because Rust follows the Box automatically. When first goes out of scope, it frees Sunrise too: one owner each, all the way down.

Rc<T>: shared ownership by counting

Rc stands for reference counted. Rc::new(value) puts the value on the heap along with a count of its owners.

  • Rc::clone(&song) adds an owner. It copies the pointer and adds 1 to the count. The song itself is not copied.
  • When an owner goes away, the count drops by 1. At 0, the value is freed.
  • The value is read-only, and Rc works on one thread. Arc is the thread-safe version.

When to use it: several parts of a program need the same value, and none of them is sure to outlast the others.

Rust Book 15.4. Python parallel: CPython counts references to every object, which is why Week 10 said Python cleans up when the last name goes away. Rc is that same idea, opted into for one value.

Two playlists, one song

This example intentionally fails to compile.

struct Song {
    title: String,
}

fn main() {
    let song = Song {
        title: String::from("Midnight Drive"),
    };

    let mut workout = Vec::new();
    let mut road_trip = Vec::new();

    workout.push(song);
    road_trip.push(song);

    println!("{} {}", workout[0].title, road_trip[0].title);
}
error[E0382]: use of moved value: `song`

Why: workout.push(song) moves the song into the first playlist, so it is gone for the second.

If one variable keeps the song alive longer than both playlists, &Song is enough. Rc is for when nothing outlives the others, such as playlists a user can delete in any order.

Try this example in Rust Playground

This is Week 10’s move error with a new type. Students may ask why not clone: that makes two separate songs, and a later change to one would not show up in the other. The references aside ties back to the first slide of the session.

Rc fixes it: both playlists own the song

use std::rc::Rc;

struct Song {
    title: String,
}

fn main() {
    let song = Rc::new(Song {
        title: String::from("Midnight Drive"),
    });
    println!("owners = {}", Rc::strong_count(&song)); // owners = 1

    let mut workout = Vec::new();
    let mut road_trip = Vec::new();

    workout.push(Rc::clone(&song));
    println!("owners = {}", Rc::strong_count(&song)); // owners = 2

    road_trip.push(Rc::clone(&song));
    println!("owners = {}", Rc::strong_count(&song)); // owners = 3

    println!("Road trip starts with {}", road_trip[0].title);
    drop(road_trip); // Delete the road trip playlist
    println!("owners = {}", Rc::strong_count(&song)); // owners = 2

    println!("Workout starts with {}", workout[0].title);
}
  • drop(road_trip) deletes the playlist early, as the end of its scope would.
  • The song is freed only when the last owner is gone.

Try this example in Rust Playground

Output: owners = 1, 2, 3, the road trip line, owners = 2, the workout line. The song variable itself is the first owner. Both playlists print the same title because they point to the same song, not two copies.

RefCell<T>: change through a shared handle

Rc values are read-only. RefCell lets you change a value even when it is shared.

  • .borrow() gives a read-only borrow, like &.
  • .borrow_mut() gives a changeable borrow, like &mut.
  • Week 10’s rules still apply: many readers, or one writer. RefCell checks them while the program runs, and breaking them stops the program with a panic.

When to use it: almost always inside an Rc, to change a value that several owners share.

Rust Book 15.5. Rust calls this interior mutability. The trade is real: mistakes that would be compile errors with & and &mut become panics at runtime, so RefCell is a last resort, not a default.

Shared values are read-only

The song now counts its plays.

This example intentionally fails to compile.

use std::rc::Rc;

struct Song {
    title: String,
    plays: u32,
}

fn main() {
    let song = Rc::new(Song {
        title: String::from("Midnight Drive"),
        plays: 0,
    });

    song.plays += 1;

    println!("{} has {} plays", song.title, song.plays);
}
error[E0594]: cannot assign to data in an `Rc`

Why: an Rc value might have other owners, so no single owner may change it. Not even the first one.

Try this example in Rust Playground

Adding mut to song does not help; the restriction is on the data inside the Rc, not the variable. This is the problem RefCell solves on the next slide.

Rc<RefCell<Song>>: one play count, shared

use std::cell::RefCell;
use std::rc::Rc;

struct Song {
    title: String,
    plays: u32,
}

fn main() {
    let song = Rc::new(RefCell::new(Song {
        title: String::from("Midnight Drive"),
        plays: 0,
    }));

    let mut workout = Vec::new();
    let mut road_trip = Vec::new();
    workout.push(Rc::clone(&song));
    road_trip.push(Rc::clone(&song));

    workout[0].borrow_mut().plays += 1; // Played from the workout list
    road_trip[0].borrow_mut().plays += 1; // Played from the road trip list

    let now = song.borrow();
    println!("{} has {} plays", now.title, now.plays); // Midnight Drive has 2 plays
}
  • Rc: both playlists own the same song.
  • RefCell: either playlist can change it.

Try this example in Rust Playground

Output: Midnight Drive has 2 plays. Each borrow_mut lasts only for its line, so the two changes never overlap. Read the type from the inside out: a Song, changeable at runtime (RefCell), with several owners (Rc). Easy to overuse: if a single owner with &mut works, use that.

Break the rules, and RefCell panics

This example compiles, then panics when it runs.

use std::cell::RefCell;

struct Song {
    title: String,
    plays: u32,
}

fn main() {
    let song = RefCell::new(Song {
        title: String::from("Midnight Drive"),
        plays: 0,
    });

    let mut editing = song.borrow_mut();
    let reading = song.borrow(); // Panics: editing is still active

    editing.plays += 1;
    println!("{} has {} plays", reading.title, reading.plays);
}
thread 'main' panicked at src/main.rs:15:24:
RefCell already mutably borrowed

Why: editing is still active, so a reader breaks the shared reference promise. The compiler could not see it; the program checks and stops.

Try this example in Rust Playground

Compare with Week 10’s “A reader and an editor can conflict” slide: same rule, same mistake, but caught at runtime with a panic instead of E0502 at compile time. That trade is why RefCell is a last resort.

Which tool do I need?

Does one owner with & and &mut work?
├─ Yes → Use ordinary ownership and borrowing. Stop here.
└─ No  → Does the type contain itself (a song with a next song)?
         ├─ Yes → Box<T>
         └─ No  → Do several parts need to own it?
                  ├─ No  → Box<T> or plain ownership
                  └─ Yes → Does it need to change?
                           ├─ No  → Rc<T>
                           └─ Yes → Rc<RefCell<T>>

Across threads: Arc<T> replaces Rc<T>, and Mutex<T> replaces RefCell<T> (Rust Book 16).

None of these smart pointers are graded in Lab 13; they are here so students can recognize them in other Rust code and in the final project. Arc and Mutex are optional reading.

Errors: recover or stop?

Situation Tool Example
A failure the caller should handle Result<T, E> Bad user input, missing file
A bug or broken assumption panic! Index out of bounds, RefCell misuse
  • Result puts the failure in the function’s signature.
  • .unwrap() and .expect("why") turn an Err into a panic: fine in tests and quick experiments.

Rust Book 9.3, “To panic! or not to panic!”. Students used Result and ? in Week 11; this session focuses on writing functions that return good errors. Python parallel: exceptions are not part of a function’s signature; Result is.

Result with match

fn parse_port(input: &str) -> Result<u16, String> {
    input
        .trim()
        .parse::<u16>()
        .map_err(|_| format!("Invalid port: {}", input))
}

fn main() {
    for input in ["8080", "http", "70000"] {
        match parse_port(input) {
            Ok(port) => println!("Port: {}", port),
            Err(message) => println!("Error: {}", message),
        }
    }
}
  • map_err converts the parse error into our own message.
  • 70000 fails too: it does not fit in a u16 (0 to 65535).

Try this example in Rust Playground

Output: Port: 8080, Error: Invalid port: http, Error: Invalid port: 70000. The type u16 does the range checking for free. The match forces both outcomes to be handled; there is no way to use the port without checking for an error first.

The ? operator

use std::num::ParseIntError;

// Without ?: every step checks and returns early by hand
#[allow(clippy::question_mark)] // Clippy would suggest ? here
fn sum_verbose(a: &str, b: &str) -> Result<i32, ParseIntError> {
    let x = match a.trim().parse::<i32>() {
        Ok(n) => n,
        Err(e) => return Err(e),
    };
    let y = match b.trim().parse::<i32>() {
        Ok(n) => n,
        Err(e) => return Err(e),
    };
    Ok(x + y)
}

// With ?: the same behavior
fn sum(a: &str, b: &str) -> Result<i32, ParseIntError> {
    let x: i32 = a.trim().parse()?;
    let y: i32 = b.trim().parse()?;
    Ok(x + y)
}

fn main() {
    println!("{:?}", sum_verbose("2", "3")); // Ok(5)
    println!("{:?}", sum("2", "3")); // Ok(5)
    println!("{:?}", sum("2", "three")); // Err(ParseIntError { kind: InvalidDigit })
}

? means: if Ok, take the value; if Err, return the error now. Clippy even suggests ? for the long version.

Custom error types: define the error

use std::fmt;

#[derive(Debug)]
enum PercentError {
    Empty,
    NotANumber(String),
    OutOfRange(i32),
}

impl fmt::Display for PercentError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            PercentError::Empty => write!(f, "input is empty"),
            PercentError::NotANumber(s) => write!(f, "{:?} is not a number", s),
            PercentError::OutOfRange(n) => write!(f, "{} is not between 0 and 100", n),
        }
    }
}
  • The enum lists every way the function can fail; some variants carry details.
  • Display (Week 12) turns each variant into a message for people.

An enum error lets callers match on the variant and react differently, which a String error cannot offer. Debug is derived for programmers; Display is written by hand because only we know the right wording. Lab 13 asks for a smaller version of this pattern with its own ParseError; this example uses different names and rules so it is not the lab answer.

Custom error types: use the error

fn parse_percent(input: &str) -> Result<i32, PercentError> {
    let input = input.trim();
    if input.is_empty() {
        return Err(PercentError::Empty);
    }
    let n: i32 = input
        .parse()
        .map_err(|_| PercentError::NotANumber(input.to_string()))?;
    if !(0..=100).contains(&n) {
        return Err(PercentError::OutOfRange(n));
    }
    Ok(n)
}

fn main() {
    for input in ["85", "", "lots", "150"] {
        match parse_percent(input) {
            Ok(n) => println!("{}%", n),
            Err(e) => println!("Error: {}", e),
        }
    }
}
85%
Error: input is empty
Error: "lots" is not a number
Error: 150 is not between 0 and 100

Putting it together

use std::num::ParseIntError;

fn parse_all(inputs: &[&str]) -> Result<Vec<i32>, ParseIntError> {
    inputs.iter().map(|s| s.trim().parse::<i32>()).collect()
}

fn main() {
    println!("{:?}", parse_all(&["1", " 2", "3 "])); // Ok([1, 2, 3])
    println!("{:?}", parse_all(&["1", "two", "3"])); // Err(ParseIntError { kind: InvalidDigit })
}
  • An iterator of Results can collect into a Result of a vector.
  • The first Err stops the chain: no partial lists to clean up.

Key takeaways
