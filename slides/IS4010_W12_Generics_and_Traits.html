Python vs. Rust abstraction philosophy: In Python, duck typing lets one function accept anything that has the right methods, and mistakes surface at runtime as AttributeError or TypeError. In Rust, the compiler needs to know at compile time which operations a type supports. Generics say “this works for many types”; traits say “these are the operations those types must support.” Neither removes the need for tests.

Routine for the week, same as Week 10: predict, run, explain.

Session 1: generic types

One function, many types?

You have written largest for a list of numbers. Now you need it for a list of characters.

  • Do you copy the function and change the types?
  • What if you also need it for floats, or for names?
  • How does the compiler know the comparison > makes sense for each type?

The problem: duplicate code

fn largest_i32(list: &[i32]) -> &i32 {
    let mut largest = &list[0];
    for item in list {
        if item > largest {
            largest = item;
        }
    }
    largest
}
fn largest_char(list: &[char]) -> &char {
    let mut largest = &list[0];
    for item in list {
        if item > largest {
            largest = item;
        }
    }
    largest
}
fn main() {
    let numbers = [34, 50, 25, 100, 65];
    println!("Largest number: {}", largest_i32(&numbers)); // 100

    let chars = ['y', 'm', 'a', 'q'];
    println!("Largest char: {}", largest_char(&chars)); // y
}

Predict: What is different between the two functions?

Try this example in Rust Playground

Answer: only the types in the signatures. The bodies are identical. This is the book’s listing 10-4. Ask: if you found a bug in this logic, how many places would you fix it? With five types, five copies.

Python parallel:

def largest(lst):
    result = lst[0]
    for item in lst:
        if item > result:
            result = item
    return result

largest([34, 50, 25, 100, 65])  # works
largest(['y', 'm', 'a', 'q'])   # also works

Python needs no duplication, but passing values that cannot be compared raises TypeError only when that line runs. Rust wants the same single function, checked before the program runs.

Read the angle brackets aloud

Ask students to read each row out loud before moving on. The last two rows appear later this session; the table is here so the syntax never arrives unannounced.

Try this example in Rust Playground

This is the book’s listing 10-5. Ask students to predict before running: most expect it to work. The body uses >, but T could be any type, including types that cannot be compared. Rust checks the generic function once, for every possible T, not separately for each call. The help line already names the fix, which the next slide applies.

Add a trait bound

fn largest<T: PartialOrd>(list: &[T]) -> &T {
    let mut largest = &list[0];
    for item in list {
        if item > largest {
            largest = item;
        }
    }
    largest
}

fn main() {
    let numbers = [34, 50, 25, 100, 65];
    println!("Largest number: {}", largest(&numbers)); // 100

    let chars = ['y', 'm', 'a', 'q'];
    println!("Largest char: {}", largest(&chars)); // y
}

Why: T: PartialOrd promises that every T can be compared, so > is allowed.

A trait bound lists what T must be able to do.

Try this example in Rust Playground

Output: Largest number: 100, then Largest char: y. The only change from the failing version is : PartialOrd after T. PartialOrd is a trait from the standard library: a named set of abilities, here “can be compared with < and >”. Session 2 is all about traits; for now, a trait bound is the instruction printed next to the blank on the form.

Python parallel: def largest(lst: list[T]) -> T with a TypeVar is the closest annotation, but Python does not enforce it at runtime. Rust rejects calls with a type that is not PartialOrd before the program runs.

Generic structs

struct Point<T> {
    x: T,
    y: T,
}

fn main() {
    let integer = Point { x: 5, y: 10 };
    let float = Point { x: 1.5, y: 4.0 };

    println!("integer: ({}, {})", integer.x, integer.y); // (5, 10)
    println!("float: ({}, {})", float.x, float.y); // (1.5, 4)
}

  • Rust fills in T from the values: i32 for integer, f64 for float.

One T means one type

This example intentionally fails to compile.

struct Point<T> {
    x: T,
    y: T,
}

fn main() {
    let wont_work = Point { x: 5, y: 4.0 };
    println!("({}, {})", wont_work.x, wont_work.y);
}
error[E0308]: mismatched types
expected integer, found
floating-point number

Fix: two blanks, Point<T, U>

    x: T,
    y: U,
}

Try the fixed version in Rust Playground

Why: x and y share one T. Once 5 makes T an integer, 4.0 does not fit.

Book listings 10-7 and 10-8. Fixed output: (5, 10), then (5, 4). The Python dataclass version would accept x=5, y=4.0 without complaint, because annotations are not enforced at runtime. In Rust the struct definition itself says whether the fields must match. Too many type parameters make code hard to read; if you need many, the book suggests restructuring.

Generic enums: Option and Result

How the standard library defines them:

enum Option<T> {      enum Result<T, E> {
    Some(T),              Ok(T),
    None,                 Err(E),
}                     }

Using Result<&str, String>:

fn validate_username(name: &str) -> Result<&str, String> {
    if name.trim().is_empty() {
        Err(String::from("Username cannot be empty"))
    } else {
        Ok(name)
    }
}

fn main() {
    for input in ["homer", "   "] {
        match validate_username(input) {
            Ok(name) => println!("Welcome, {}!", name),
            Err(message) => println!("Error: {}", message),
        }
    }
}

Try this example in Rust Playground

Output: Welcome, homer!, then Error: Username cannot be empty. The definitions are shown as text because they are already in the standard library; redefining them in our own program would only shadow the real ones. Students used both enums in Week 11; the point here is that they are ordinary generic enums, not special syntax. Result has two blanks: T for success and E for the error.

Python parallel: Optional[T] or T | None is an annotation; nothing forces the caller to handle None. Rust’s Option forces a match or a method such as unwrap_or. Python signals failure by raising exceptions, which do not appear in the function’s signature; Result puts the failure case in the signature.

Generic methods

struct Point<T> {
    x: T,
    y: T,
}

impl<T> Point<T> {
    fn x(&self) -> &T {
        &self.x
    }
}
impl Point<f32> {
    fn distance_from_origin(&self) -> f32 {
        (self.x.powi(2) + self.y.powi(2)).sqrt()
    }
}

fn main() {
    let p = Point { x: 5, y: 10 };
    println!("p.x = {}", p.x()); // 5

    let q: Point<f32> = Point { x: 3.0, y: 4.0 };
    println!("distance = {}", q.distance_from_origin()); // 5
}
  • impl<T> Point<T>: methods for every Point.
  • impl Point<f32>: methods only for Point<f32>.

Predict: Can p, a Point of integers, call distance_from_origin?

No: E0599: no method named distance_from_origin found for struct Point<{integer}>. Only Point<f32> has it.

Try this example in Rust Playground

Book listings 10-9 and 10-10. Output: p.x = 5, then distance = 5. Read impl<T> Point<T> with the table: “for any T, here are methods for Point of T.” The after impl declares the blank; without it, Rust would look for a concrete type named T. powi and sqrt exist for floats, which is why that method is limited to Point.

Python parallel: a Python Point class could define distance_from_origin for every point, and it would fail at runtime for non-numeric fields. Rust attaches the method only where it makes sense.

What the compiler does with generics

You write one generic definition. For each type you use, the compiler writes a specific copy:

You write:                    The compiler generates:

let integer = Some(5);        enum Option_i32 { Some(i32), None }
let float = Some(5.0);        enum Option_f64 { Some(f64), None }
  • This is called monomorphization (“making one shape”).
  • The program runs the specific copies, as if you had written largest_i32 and largest_char yourself.

You write it once; the compiler writes the copies.

This is the book’s own illustration from 10.1, “Performance of code using generics.” The names Option_i32 and Option_f64 are for illustration; the real generated names are internal. The practical consequence: generics are checked once and specialized at compile time, so there is no runtime cost to looking up the type. The trade-off is more compiled code when many types are used. Avoid promising “zero cost” in every situation; the honest claim is no dynamic type lookup for these calls.

Session 2: traits

What can a type do?

A trait is a named list of things a type can do.

  • Think of a job description: “Must be able to summarize itself.”
  • Any type can apply for the job by implementing the trait.
  • The compiler checks that every listed task is done before it accepts the type.

PartialOrd from session 1 is a trait: “can be compared with < and >.”

Keep the job-description analogy running through the session: a trait is the job description, impl Trait for Type is the type’s application, and a trait bound is a hiring requirement (“only applicants who can do X”). Traits are Rust’s way to share behavior between types without class inheritance.

Python parallel: the closest match is typing.Protocol or an abstract base class. The key difference: in Rust, a type only has a trait if it says so with impl Summary for Tweet. Having a method with the right name is not enough.

Define and implement a trait

trait Summary {
    fn summarize(&self) -> String;
}

struct Tweet {
    username: String,
    content: String,
}

impl Summary for Tweet {
    fn summarize(&self) -> String {
        format!("{}: {}", self.username, self.content)
    }
}

fn main() {
    let tweet = Tweet {
        username: String::from("horse_ebooks"),
        content: String::from("of course, as you probably already know"),
    };
    println!("1 new tweet: {}", tweet.summarize());
}
  • trait Summary lists the method signature, with no body.
  • impl Summary for Tweet provides the body for Tweet.

Try this example in Rust Playground

Output: 1 new tweet: horse_ebooks: of course, as you probably already know. Book listings 10-12 and 10-13, trimmed to the fields we use. The semicolon after the trait’s fn signature means “every implementer must write this.” Note the method is called with dot syntax exactly like Week 11’s impl methods.

Default implementations

trait Summary {
    fn summarize_author(&self) -> String;

    fn summarize(&self) -> String {
        format!("(Read more from {}...)", self.summarize_author())
    }
}

struct Tweet {
    username: String,
}

impl Summary for Tweet {
    fn summarize_author(&self) -> String {
        format!("@{}", self.username)
    }
    // summarize() uses the default
}

fn main() {
    let tweet = Tweet {
        username: String::from("horse_ebooks"),
    };
    println!("1 new tweet: {}", tweet.summarize());
}
  • summarize_author has no body: every type must write it.
  • summarize has a body: types get it for free, or override it.

Traits as parameters

Add to the Tweet and NewsArticle program:

fn notify(item: &impl Summary) {
    println!("Breaking news! {}", item.summarize());
}

fn main() {
    let tweet = Tweet {
        username: String::from("horse_ebooks"),
        content: String::from("of course, as you probably already know"),
    };
    let article = NewsArticle {
        headline: String::from("Penguins win the Stanley Cup!"),
        author: String::from("Iceburgh"),
    };

    notify(&tweet);
    notify(&article);
}

Read it as: notify accepts a reference to any type that implements Summary.

Predict: What happens with notify(&String::from("hello"))?

E0277: the trait bound String: Summary is not satisfied. String never applied for the job.

Try the full program in Rust Playground

Output: Breaking news! horse_ebooks: …, then Breaking news! Penguins win the Stanley Cup!, by Iceburgh. This is where generics and traits meet: one function, many types, and a requirement on what those types can do. Python’s equivalent is a Protocol type hint, which a type checker can flag but the runtime ignores.

Three ways to write the same requirement

Signature Read it as
fn notify(item: &impl Summary) Any type that can summarize
fn notify<T: Summary>(item: &T) Same thing, with the type named T
fn notify<T: Summary + Display>(item: &T) T must summarize and print with {}

Predict: Do these mean the same thing?

fn notify(item1: &impl Summary, item2: &impl Summary)
fn notify<T: Summary>(item1: &T, item2: &T)

No. The first accepts a Tweet and a NewsArticle together. The second forces both items to be the same type T.

This is the book’s “Trait bound syntax” discussion. impl Summary is shorthand for a trait bound; naming the type T lets you say “these two must match.” The + form needs use std::fmt::Display;. Rule of thumb: use impl Trait for simple cases, a named T when the type appears more than once.

where clauses for long bounds

use std::fmt::{Debug, Display};

// Bounds written inline
fn describe_inline<T: Display + PartialOrd, U: Debug>(a: &T, b: &T, extra: &U) -> String {
    let bigger = if a > b { a } else { b };
    format!("{} wins; extra: {:?}", bigger, extra)
}

// The same bounds in a where clause
fn describe<T, U>(a: &T, b: &T, extra: &U) -> String
where
    T: Display + PartialOrd,
    U: Debug,
{
    let bigger = if a > b { a } else { b };
    format!("{} wins; extra: {:?}", bigger, extra)
}

fn main() {
    println!("{}", describe_inline(&3, &7, &[1, 2])); // 7 wins; extra: [1, 2]
    println!("{}", describe(&"Homer", &"Bart", &(1, 2))); // Homer wins; extra: (1, 2)
}

Both functions are identical. where moves the bounds below the signature so the name and parameters stay readable.

Try this example in Rust Playground

Output: 7 wins; extra: [1, 2], then Homer wins; extra: (1, 2). Strings compare alphabetically, and “Homer” comes after “Bart”. With bounds this short, either style is fine; where pays off as the list grows. Rule of thumb: if the signature no longer fits on one line, use where. The bounds are what the body needs: PartialOrd for >, Display for {}, Debug for {:?}.

Returning a type that implements a trait

Add to the Tweet program:

fn make_tweet() -> impl Summary {
    Tweet {
        username: String::from("horse_ebooks"),
        content: String::from("of course, as you probably already know"),
    }
}

fn main() {
    let item = make_tweet();
    println!("1 new tweet: {}", item.summarize());
}

Read it as: make_tweet returns some type that implements Summary; the caller does not need to know which.

Limitation: All branches must return the same type. Returning a Tweet in one branch and a NewsArticle in another fails with E0308: if and else have incompatible types.

Traits you already know

Standard library traits

Python’s dunder methods are the best bridge: special methods the language knows how to call. Clone’s behavior depends on the type: String::clone copies the text, while cloning a reference-counted pointer (Week 13) only bumps a count, so avoid “deep copy” as a definition.

More traits for reference: Copy (implicit duplication, as with integers in Week 10), Eq and Ord (stricter versions of PartialEq and PartialOrd; f64 has only the partial versions because NaN != NaN), Hash (HashMap keys), and Default (Type::default()).

Deriving traits

#[derive(Debug, Clone, PartialEq)]
struct Point {
    x: i32,
    y: i32,
}

fn main() {
    let p1 = Point { x: 1, y: 2 };
    let p2 = p1.clone(); // Clone

    println!("{:?}", p1); // Debug: Point { x: 1, y: 2 }
    println!("equal? {}", p1 == p2); // PartialEq: true
}
  • #[derive(...)] asks the compiler to write the trait implementations for you.
  • You have used #[derive(Debug)] since Week 11.
  • Derivable: Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash, Default.

Try this example in Rust Playground

Output: Point { x: 1, y: 2 }, then equal? true. Derived implementations work field by field: two Points are equal when every field is equal. Derive fails if a field’s type does not implement the trait. Python parallel: @dataclass generates repr and eq the same way.

Implementing Display

use std::fmt;

struct Point {
    x: i32,
    y: i32,
}

impl fmt::Display for Point {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "({}, {})", self.x, self.y)
    }
}

fn main() {
    let p = Point { x: 1, y: 2 };
    println!("Point: {}", p); // Point: (1, 2)
}

Why not derive it? There is no single right way to show a Point to a user: (1, 2), 1,2, or x=1 y=2. You choose.

Try this example in Rust Playground

Output: Point: (1, 2). Lab 12 asks for this same pattern on Stack. Walk through the parts: use std::fmt brings the module into scope; fn fmt has the exact signature the trait requires; write! works like format! but writes into f and returns fmt::Result. Implementing Display also gives .to_string() for free.

Python parallel: def str(self): return f”({self.x}, {self.y})“.

Implementing Iterator

struct Counter {
    count: u32,
}

impl Counter {
    fn new() -> Counter {
        Counter { count: 0 }
    }
}

impl Iterator for Counter {
    type Item = u32;

    fn next(&mut self) -> Option<Self::Item> {
        if self.count < 5 {
            self.count += 1;
            Some(self.count)
        } else {
            None
        }
    }
}
fn main() {
    for n in Counter::new() {
        print!("{} ", n); // 1 2 3 4 5
    }
    println!();

    let total: u32 = Counter::new().sum();
    println!("sum = {}", total); // 15
}
  • Implement one required method, next, and you can use for loops and default methods like .sum().
  • type Item = u32; says what kind of value next returns.

Try this example in Rust Playground

Output: 1 2 3 4 5, then sum = 15. This is the default-implementation idea at scale: next is required, and map, filter, sum, take, and many others are provided. Putting it together: Lab 12’s Stack<T>

pub struct Stack<T> {
    data: Vec<T>,
}

impl<T> Stack<T> {
    pub fn new() -> Self
    pub fn push(&mut self, item: T)
    pub fn pop(&mut self) -> Option<T>
    pub fn peek(&self) -> Option<&T>
    pub fn is_empty(&self) -> bool
    pub fn len(&self) -> usize
}

impl<T: fmt::Debug> fmt::Display for Stack<T>
  • Generics: one Stack<T> holds i32, String, or f64.
  • Traits: Display prints any stack whose items implement Debug.

These are the signatures from week12/src/main.rs, without bodies; students implement them. Read each line with the angle-bracket table. peek returns Option<&T> because it only looks; pop returns Option because the item leaves the stack and ownership moves to the caller (Week 10). The Display impl is bounded by T: fmt::Debug, so each item can be formatted with {:?}.

Python parallel: a Python list already acts as a stack (append, pop, [-1]). The Rust version is a typed contract: a Stack can only hold i32 values.

Key takeaways

  • Generics: write the code once with a placeholder type T.
  • Traits: name what a type can do, like a job description.
  • Trait bounds: connect them, “any T that can do this.”
  • The compiler checks the requirements before the program runs, then writes a specific copy for each type you use.

Read signatures aloud: fn largest<T: PartialOrd>(list: &[T]) -> &T is “for any comparable type T, take a slice of T and return a reference to one.”

Python-to-Rust cheat sheet for review:

Python Rust
Duck typing Trait bounds, checked at compile time
Optional[T] Option<T>
Exceptions Result<T, E>
__str__ / __repr__ Display / Debug
__eq__ / __lt__ PartialEq / PartialOrd
__iter__ / __next__ Iterator with next()
ABC abstract method Required trait method
ABC concrete method Default trait method
@dataclass #[derive(...)]

Neither approach is universally better; Rust moves more checks to compile time, and both still need tests.
